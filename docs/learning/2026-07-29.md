As checked on 2026-07-29, Databricks documents `from_json(jsonStr, schema [, options])` for parsing a JSON string into a struct matching the provided schema. Outside Lakeflow pipelines, the schema must be provided explicitly. The docs also call out case sensitivity for field names and parser modes such as permissive and fail-fast behavior.

Databricks SQL can query JSON strings directly with the `:` operator, dot notation, bracket notation for case-sensitive or special-character fields, array indexing, and casts. The same documentation recommends extracting nested columns with correct data types for better read performance when the shape is known.

The VARIANT documentation recommends VARIANT over JSON strings for semi-structured data on supported runtimes, while also noting limitations: VARIANT cannot be used directly for clustering keys, partitions, Z-order keys, comparisons, grouping, ordering, or set operations. That makes VARIANT useful for exploratory raw storage, while typed fields remain the safer silver/gold publication shape.

The Auto Loader schema documentation explains that the rescued data column stores fields that do not match schema because of missing columns, type mismatches, or case mismatches. The rescued data column contains a JSON blob with rescued columns plus source file path. This is the production counterpart to the lab's `schema_drift_json` and quarantine evidence.

## What I Learned

Nested JSON parsing is a modeling decision, not just a syntax task.

Raw bronze should preserve the payload, source file path, batch id, and ingestion timestamp. Without that evidence, parse failures cannot be replayed or explained.

`from_json` is the right tool when a JSON blob has a known contract and downstream tables need typed columns. It turns a string into a struct with nested arrays and structs, so SQL and PySpark can access fields with `order_doc.customer.customer_id` or `order_doc.items`.

Direct JSON-string extraction with the `:` operator is useful for targeted fields, escaped names, array indexes, and drift evidence. It is weaker as a long-term silver model because values often remain strings unless explicitly cast.

`explode` changes table grain. The item table is one row per item, not one row per order. Aggregates must join back only to quality-approved orders, or quarantined child records will leak into metrics.

VARIANT is a useful raw/exploratory shape on supported runtimes, especially when nested payloads change often. But governed publication still benefits from typed columns because VARIANT has limitations around clustering, partitioning, grouping, ordering, and comparisons.

Quality gates must inspect both parent and child fields. A payload can parse successfully while still having empty arrays, bad quantities, missing customer identifiers, or unreconciled totals.

## PySpark Notes

The notebook uses PySpark in Lab Part 4 to score typed bronze rows.

```python
bronze_df = spark.table("de_learning.orders_nested_bronze_day30")
```

SQL equivalent:

```sql
SELECT
  order_doc.order_id,
  order_doc.customer.customer_id,
  size(order_doc.items) AS item_count,
  CASE
    WHEN parse_status <> 'PARSED' THEN 'QUARANTINE_PARSE'
    WHEN order_doc.order_id IS NULL THEN 'QUARANTINE_REQUIRED_KEYS'
    ELSE 'PASS'
  END AS quality_status
FROM orders_nested_bronze_day30;
```

Practical syntax notes:

- `spark.table(...)` reads the Delta table into a DataFrame.
- `F.col("order_doc.order_id")` references a nested struct field.
- `withColumn(...)` adds quality fields such as `item_count`, `has_bad_item`, and `quality_status`.
- `F.expr(...)` lets PySpark use SQL higher-order functions such as `aggregate` and `exists`.
- `where(...)` filters quarantine rows before writing them to a separate table.
- DataFrame transformations are lazy until `write.saveAsTable(...)` or `display(...)` runs.

## Mistakes / Confusions

- `from_json` needs an explicit schema outside Lakeflow pipeline schema inference.
- Field names in `from_json` schemas are case-sensitive.
- A parsed struct does not prove the business record is publishable.
- Empty arrays are easy to drop accidentally with `explode`.
- `explode_outer` preserves parent context for null arrays, while plain `explode` produces no rows for null collections.
- Direct JSON-string extraction can be convenient but may leave values as strings.
- VARIANT is not a replacement for every modeled table because key optimization and grouping limitations matter.
- Schema drift should be evidence, not a silent parser side effect.

## Revision Cards

Q: What does `from_json` return in Databricks SQL?
A: A struct value whose fields and types match the supplied schema.

Q: When must you provide an explicit schema to `from_json`?
A: When using it outside Lakeflow pipeline schema inference.

Q: Why keep the raw JSON payload after parsing?
A: It supports replay, quarantine review, audit, and parser debugging.

Q: What does `explode` do to an array column?
A: It creates one output row per array element.

Q: Why is array explosion a modeling decision?
A: It changes the row grain, which changes downstream metric semantics.

Q: What is the difference between `explode` and `explode_outer`?
A: `explode` produces no rows for null collections; `explode_outer` can retain a row with null values.

Q: Why can a successfully parsed JSON row still be quarantined?
A: Required keys, child values, empty arrays, or totals can still fail business quality checks.

Q: What does Auto Loader rescued data preserve?
A: Fields that do not match schema because of missing columns, type mismatches, or case mismatches, plus source file path.

Q: When is VARIANT useful?
A: For flexible raw or exploratory semi-structured data on supported runtimes.

Q: Why not publish every downstream table directly from VARIANT?
A: VARIANT has limitations around clustering, partitioning, grouping, ordering, comparisons, and set operations.

Q: What should silver tables contain after nested JSON parsing?
A: Typed, quality-approved fields at an explicit grain.

Q: What is the operational value of `schema_drift_json`?
A: It gives reviewers evidence of unexpected fields without silently promoting them.
