## Theory Anchors

- Auto Loader supports schema inference and evolution using a schema location. Each ingestion workload needs its own schema-location state for reliable operations.
- For JSON, CSV, and XML, Auto Loader avoids type-evolution surprises by defaulting many fields to strings unless type inference or schema hints are used.
- The rescued data column captures data that cannot be parsed because of type mismatch, schema mismatch, or column casing mismatch. Auto Loader includes rescued-data support, while legacy `COPY INTO` does not support the rescued data column.
- `readerCaseSensitive` controls whether fields that differ only by case are rescued or read case-insensitively when rescued data is enabled.
- `columnNameOfCorruptRecord` captures malformed records for Auto Loader parsing so bad payloads are not silently discarded.
- Lakeflow pipeline `from_json` can infer and evolve schemas when used with a unique `schemaLocationKey`; outside that setting, `from_json` requires an explicit schema.
- Databricks recommends Variant over JSON strings for flexible semi-structured storage when changing or unknown schema is the main requirement.
- `explode` unnests arrays or maps, and `explode_outer` keeps source rows even when an array is null.

## What I Learned

- Semi-structured ingestion is not complete when JSON parses. Publication needs gates for required fields, nested item quality, PII drift, and corrupt payloads.
- Rescue data is valuable because it separates additive drift from data loss. A new optional field can be reviewed without blocking canonical fields.
- Case mismatch is a contract issue when canonical field names matter. With `readerCaseSensitive`, wrong-case fields can be rescued instead of silently mapped.
- Corrupt JSON is not schema evolution. It belongs in quarantine with raw payload evidence.
- PII in rescued data must be treated as a governance incident, not just schema drift.
- Silver tables should expose typed, contract-safe fields and nested item projections, while bronze keeps raw and rescued evidence.

## PySpark Notes

The PySpark lab builds `semistructured_quality_decisions_day34`.

- `bronze_df` represents parsed JSON plus `_rescued_data` and `_corrupt_record`.
- `item_df` represents one row per nested item after `explode_outer`.
- `decision_df` represents one publish or quarantine decision per source file.
- SQL equivalent: `LATERAL VIEW explode(items)` for item checks, aggregate back to source file, then `CASE WHEN` for the publish gate.
- `F.explode_outer(F.col("items"))` keeps records even when the nested array is null.
- `groupBy(...).agg(...)` changes the grain from item rows back to source files.
- `withColumn` creates flags such as `rescued_data_present`, `corrupt_record_present`, and `decision_action`.
- The DataFrame plan is lazy until `.write.saveAsTable(...)` and `display(...)`.

## Mistakes / Confusions

- Do not publish from bronze just because `from_json` returns a struct; required fields can still be null.
- Do not treat all rescued data the same. Additive optional drift, type mismatch, case mismatch, and PII rescue have different actions.
- Do not let corrupt JSON trigger schema evolution work. The producer must repair or replay the payload.
- Do not flatten nested arrays before row-level publish gates pass.
- Do not disable case-sensitive rescue unless the producer contract explicitly permits case-insensitive fields.
- Do not hide PII drift inside a generic schema-evolution backlog.

## Revision Cards

1. **Q:** What is `_rescued_data` for?
   **A:** It preserves data that cannot be parsed due to type mismatch, schema mismatch, or casing mismatch.

2. **Q:** What is `_corrupt_record` for?
   **A:** It preserves malformed records that cannot be parsed.

3. **Q:** Why keep raw JSON in bronze?
   **A:** It is the audit source for replay, producer fixes, and contract negotiation.

4. **Q:** When can additive rescued data still publish?
   **A:** When canonical required fields pass and the drift is optional, non-PII, and reviewed by the contract owner.

5. **Q:** Why is case mismatch dangerous?
   **A:** Wrong-case fields can leave canonical required fields null, even though the data appears present.

6. **Q:** Why quarantine unexpected PII?
   **A:** It changes the governance and compliance posture of the table.

7. **Q:** Why explode nested arrays only after row-level gates?
   **A:** Item projections should not publish rows from an order that failed contract or governance checks.

8. **Q:** What does `schemaLocationKey` do in Lakeflow `from_json`?
   **A:** It gives each evolving JSON expression a unique schema-tracking key inside the pipeline.
