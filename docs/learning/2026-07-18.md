## What I Learned

Compute choice is not just "what cluster do I attach?" It is an operational decision about latency, cost, isolation, governance, configurability, and failure diagnosis.

The practical decision tree:

```text
SQL analytics / BI / dashboard -> SQL warehouse, usually serverless when available
Notebook exploration -> serverless notebook compute when supported; all-purpose only when justified
Automated job, no custom cluster needs -> serverless job compute when supported
Automated job needing custom cluster settings -> classic jobs compute with policy controls
Lakeflow pipeline -> serverless pipeline compute when supported
Production workload on all-purpose compute -> usually a smell
```

Serverless compute reduces operational surface area: faster startup, fewer cluster settings, and on-demand scaling. Classic compute still matters when a workload needs custom cluster configuration, custom networking, unsupported features, or specific operational constraints.

SQL warehouses are separate because SQL workloads optimize around query concurrency, queueing behavior, dashboard latency, auto-stop, and warehouse scaling. A SQL dashboard should not be forced onto a general-purpose Spark cluster just because the team already has one.

All-purpose compute is useful for interactive development, but risky for production jobs. It can hide state, create idle cost, blur ownership, and make job runs less reproducible.

Principal-level point: a compute recommendation is incomplete unless it names the workload shape, selected compute, rejected alternatives, policy guardrails, owner/cost tags, and the symptoms that would trigger reassessment.

## PySpark Notes

The notebook uses PySpark to score compute choices.

```python
candidate_df = (
    workloads_df.crossJoin(options_df)
    .where(
        ((F.col("primary_language") == "sql") & F.col("supports_sql"))
        | ((F.col("primary_language").isin("pyspark", "python_sql")) & F.col("supports_python"))
    )
)
```

SQL equivalent:

```sql
SELECT *
FROM workload_profiles_day20 w
CROSS JOIN compute_options_day20 c
WHERE
  (w.primary_language = 'sql' AND c.supports_sql)
  OR (w.primary_language IN ('pyspark', 'python_sql') AND c.supports_python);
```

Important syntax:

- `spark.table(...)` loads SQL tables into DataFrames.
- `crossJoin(...)` creates all workload/compute combinations.
- `.where(...)` filters invalid candidates.
- `F.col(...)` references columns in expressions.
- `withColumn(...)` adds scoring columns.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `Window.partitionBy(...).orderBy(...)` ranks candidates per workload.
- `row_number().over(window)` picks the best candidate per workload.
- PySpark transformations are lazy until an action such as `display(...)` or table write runs.

## Mistakes / Confusions

- A compute option can support the language and still be the wrong operational choice.
- Serverless is often the default, but not universal; feature limitations and custom requirements still matter.
- Classic jobs compute is not obsolete; it is the right fallback when production jobs need custom settings.
- All-purpose compute is convenient, but it should not quietly become production job infrastructure.
- SQL warehouses should be evaluated with SQL-specific signals: query queues, concurrency, dashboard latency, warehouse scaling, and auto-stop behavior.
- Expensive or slow jobs are not always solved by more workers. Shuffle spill, skew, file layout, join strategy, and query profile can matter more.
- Compute policies are not paperwork; they enforce cost, security, runtime, tagging, and scale limits.

## Revision Cards

Q: What compute should usually run SQL dashboards?
A: A SQL warehouse, usually serverless when available.

Q: When is classic jobs compute justified?
A: When a scheduled production job needs custom cluster settings, libraries, networking, or features not available on serverless.

Q: Why avoid all-purpose compute for production jobs?
A: It can hide shared state, create idle cost, blur ownership, and reduce reproducibility.

Q: What should you check before increasing warehouse size?
A: Query queues, query profile, concurrency, warehouse scaling limits, and query efficiency.

Q: What symptoms point to Spark skew?
A: High skew ratio, long-tail tasks, high shuffle spill, and a few tasks taking much longer than the rest.

Q: What does startup time tell you?
A: Whether cold-start overhead or wrong compute choice is hurting SLA.

Q: What should compute policies enforce?
A: Worker limits, auto-termination, runtime choices, tags, production restrictions, library rules, and cost controls.

Q: What is the principal-level compute decision artifact?
A: Workload profile, selected compute, rejected alternatives, policy guardrails, owner/cost tags, and incident reassessment signals.
