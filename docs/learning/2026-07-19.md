## What I Learned

`DESCRIBE DETAIL` answers "what does this table look like physically right now?" It gives useful metadata such as table location, format, file count, size, table properties, partition columns, and statistics. Operationally, it is the first inspection point for file layout, table format, and maintenance posture.

`DESCRIBE HISTORY` answers "what happened to this table over time?" It shows Delta versions, operations, users, timestamps, operation parameters, and operation metrics. Operationally, it is how you debug bad writes, verify maintenance, inspect write patterns, and support rollback/time-travel reasoning.

`OPTIMIZE` is safe layout maintenance. On large real tables it compacts small files and improves scan efficiency. On a tiny learning table, the visible physical benefit may be small, but the history entry is still useful because it teaches how maintenance appears in table history.

`VACUUM` is different. It deletes data files no longer referenced by the current Delta table state. That can break time travel and rollback if retention is too aggressive. The safe operational pattern is:

```text
check required time-travel window
check table retention policy
run VACUUM ... DRY RUN
review files that would be deleted
only then run VACUUM without DRY RUN
```

Layout choice should follow workload:

- Small table: no manual layout until evidence says otherwise.
- Large table with mixed filters: liquid clustering is usually preferred for new Databricks tables.
- Date-scoped raw replay: coarse date partitioning can be reasonable.
- Existing legacy ZORDER: may remain until a rewrite/migration point.
- High-cardinality partitioning: usually a mistake because it creates many tiny partitions.

Principal-level point: maintenance is not a command; it is a policy-controlled workflow. The durable artifact should include detail, history, layout evidence, retention requirement, dry-run result, and the decision gate.

## PySpark Notes

The notebook uses PySpark to evaluate maintenance gates.

```python
detail_df = spark.sql("DESCRIBE DETAIL de_learning.orders_maintenance_day21")
history_df = spark.sql("DESCRIBE HISTORY de_learning.orders_maintenance_day21")
```

SQL equivalent:

```sql
DESCRIBE DETAIL de_learning.orders_maintenance_day21;
DESCRIBE HISTORY de_learning.orders_maintenance_day21;
```

The PySpark advantage is that the result becomes a DataFrame that can be joined with policy tables.

Important syntax:

- `spark.sql(...)` runs SQL and returns a DataFrame.
- `agg(...)` summarizes history rows.
- `F.sum(F.when(...))` is conditional counting, like `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`.
- `join(..., how="left")` adds optional detail/history context to policy rows.
- `select(...)` chooses and derives output columns.
- `unionByName(...)` stacks multiple check-result DataFrames with the same column names.
- `createOrReplaceTempView(...)` makes PySpark output queryable from SQL cells.
- PySpark is lazy until an action such as `display(...)`, `count()`, or table write executes the plan.

## Mistakes / Confusions

- `DESCRIBE DETAIL` and `DESCRIBE HISTORY` answer different questions. Detail is current physical state; history is operational timeline.
- `OPTIMIZE` is not a correctness fix. It improves file layout and scan efficiency.
- `VACUUM` can break time travel if files needed for older versions are removed.
- `VACUUM ... DRY RUN` returning no files on a new table is expected.
- Retention should be driven by rollback, audit, and consumer requirements, not just storage cost.
- Partitioning by high-cardinality columns such as `order_id` is usually harmful.
- Liquid clustering should be evaluated for new large Databricks tables with evolving query patterns.
- Predictive optimization can reduce maintenance burden, but teams still need policy evidence and monitoring.

## Revision Cards

Q: What does `DESCRIBE DETAIL` tell you?
A: Current table metadata: format, location, file count, size, properties, partition columns, and statistics.

Q: What does `DESCRIBE HISTORY` tell you?
A: Delta table version history: operations, users, timestamps, parameters, and metrics.

Q: Why is `OPTIMIZE` useful?
A: It improves data file layout, often by compacting small files for more efficient reads.

Q: Why is `VACUUM` risky?
A: It deletes old data files and can break time travel or rollback if retention is too short.

Q: Why run `VACUUM ... DRY RUN` first?
A: It shows which files would be deleted without deleting them.

Q: When is partitioning useful?
A: When filters are low-cardinality, stable, and aligned with data lifecycle, such as coarse dates.

Q: Why avoid high-cardinality partitioning?
A: It creates too many tiny partitions and worsens operational overhead.

Q: What is liquid clustering for?
A: Databricks-managed data layout for large tables with query filters that benefit from clustering without rigid partition directories.

Q: What should a maintenance gate protect?
A: Time travel, rollback, audit, file layout, cost, query performance, and consumer expectations.
