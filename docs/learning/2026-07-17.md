## What I Learned

Managed tables are the default and preferred table type in Unity Catalog because Databricks manages metadata, storage location, lifecycle, and optimizations. If a managed table is dropped, its metadata is removed and underlying data files are deleted after the recovery period.

External tables are different. Unity Catalog manages metadata and governs access through Databricks, but the data files live in cloud storage that you manage. Dropping an external table removes table metadata, but the files remain in the cloud bucket. External tables are useful for existing cloud data, data that must be read by non-Databricks tools, or formats/workflows that cannot be moved immediately.

Volumes are for files, not tables. Managed volumes use Databricks-managed storage. External volumes govern existing cloud storage paths. External volumes help govern file access inside Databricks, but external systems with direct cloud access can bypass Unity Catalog.

The hierarchy to remember:

```text
storage credential -> external location -> external table / external volume
catalog/schema managed storage -> managed table / managed volume
```

Principal-level point: storage lifecycle operations should be treated as change requests. Before dropping or migrating anything, check dependencies, table type, storage owner, direct cloud access, recovery window, consumer cutover, rollback, and cleanup owner.

## PySpark Notes

The notebook uses PySpark to evaluate lifecycle requests.

```python
lifecycle_decision_df = (
    requests_df
    .join(assets_df, on="asset_name", how="inner")
    .join(dependency_summary_df, on="asset_name", how="left")
    .join(location_context_df, on="external_location_name", how="left")
    .na.fill({"dependency_count": 0, "high_dependency_count": 0})
    .withColumn("storage_lifecycle_risk", ...)
    .withColumn("decision", ...)
)
```

SQL equivalent:

```sql
SELECT
  r.request_id,
  r.asset_name,
  CASE
    WHEN r.requested_action = 'DROP' AND d.high_dependency_count > 0
      THEN 'BLOCK_DEPENDENCIES_EXIST'
    WHEN r.requested_action = 'DROP' AND a.storage_model = 'external'
      THEN 'NEEDS_STORAGE_OWNER_REVIEW'
    ELSE 'NEEDS_MANUAL_REVIEW'
  END AS decision
FROM lifecycle_requests_day19 r
JOIN uc_storage_assets_day19 a USING (asset_name)
LEFT JOIN dependency_summary d USING (asset_name);
```

Important syntax:

- `spark.table(...)` loads SQL tables into DataFrames.
- `groupBy(...).agg(...)` summarizes dependencies per asset.
- `join(..., how="left")` keeps lifecycle requests even when optional context is missing.
- `.na.fill(...)` replaces missing dependency counts after a left join.
- `withColumn(...)` adds lifecycle risk, decision, and required action fields.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `array_join(collect_set(...))` creates readable dependency evidence.

## Mistakes / Confusions

- Dropping an external table does not delete files.
- Dropping a managed table eventually deletes files after the recovery window.
- Unity Catalog access control can be bypassed if users or systems have direct access to cloud files outside Databricks.
- External locations should be path-scoped; granting broad storage credential privileges is riskier.
- Volumes are for non-tabular files and workload support files, not Delta table records.
- Migration is not just copying data; it needs schema freeze, validation, replay, consumer cutover, rollback window, and cleanup ownership.
- A read-only external location can block writes even if the underlying IAM role permits them.

## Revision Cards

Q: What is a managed table?
A: A Unity Catalog table where Databricks manages metadata, storage location, data lifecycle, and optimizations.

Q: What happens when a managed table is dropped?
A: Metadata is dropped and data files are deleted after the recovery period.

Q: What is an external table?
A: A Unity Catalog table whose files live in cloud storage managed outside Databricks.

Q: What happens when an external table is dropped?
A: Table metadata is dropped, but the underlying cloud files remain.

Q: What is a storage credential?
A: A Unity Catalog object that encapsulates cloud identity access to storage.

Q: What is an external location?
A: A securable object that combines a cloud path with a storage credential.

Q: What are volumes for?
A: Governed access to non-tabular files and workload support files.

Q: Why is direct cloud access risky?
A: External systems can bypass Unity Catalog governance if they access the files directly.

Q: What should a storage migration runbook include?
A: Schema freeze, target creation, row-count validation, checksum validation, final replay, consumer cutover, rollback retention, and cleanup owner.
