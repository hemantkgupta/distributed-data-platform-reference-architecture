## What I Learned

`COPY INTO` is strong for bounded, SQL-first batch ingestion when source files are immutable. Its idempotency is useful for retries because already-loaded files are skipped on rerun.

That guarantee is not the same as business-key idempotency. If two different files carry the same `order_id`, file-level audit can still be perfect while the target contains duplicate business keys. The duplicate check belongs before silver promotion.

Malformed records need explicit evidence. In this lab, `orders_003_bad_amount.json` fails validation and lands in `orders_quarantine_day27`, while valid files load to `orders_delta_day27`. The audit table records both loaded and quarantined files so reruns do not keep rediscovering already-reviewed bad inputs.

Force reload is dangerous because it bypasses the normal skip-already-loaded behavior. It should be allowed only when there is:

- A prior audit record for the file.
- A changed hash or clear source correction evidence.
- Owner approval.
- A reconciliation query.
- A backout plan.
- Duplicate-key remediation when a reload may create duplicates.

## PySpark Notes

The notebook uses PySpark in Lab Part 5 to score force reload requests.

```python
audit_df = spark.table("de_learning.copy_into_file_audit_day27")
requests_df = spark.table("de_learning.force_reload_requests_day27")
```

SQL equivalent:

```sql
SELECT
  r.request_id,
  CASE
    WHEN a.file_path IS NULL THEN 'REJECT_FORCE_USE_NORMAL_COPY'
    WHEN NOT r.has_owner_approval OR NOT r.has_reconciliation_query THEN 'BLOCK_MISSING_FORCE_EVIDENCE'
    WHEN r.expected_duplicate_business_keys > 0 THEN 'APPROVE_FORCE_WITH_DEDUPE_RECONCILIATION'
    ELSE 'APPROVE_FORCE_RELOAD'
  END AS force_decision
FROM force_reload_requests_day27 r
LEFT JOIN copy_into_file_audit_day27 a
  ON r.file_path = a.file_path;
```

Practical syntax notes:

- `spark.table(...)` reads a Databricks table into a DataFrame.
- `F.col(...)` references a column in expressions without relying on string SQL.
- `groupBy(...).agg(...)` produces one audit summary row per source file.
- `withColumn(...)` adds derived flags such as `file_previously_audited`, `hash_changed`, and `force_decision`.
- `F.when(...).otherwise(...)` is DataFrame syntax for SQL `CASE WHEN`.
- `write.mode("overwrite").saveAsTable(...)` persists the DataFrame as a Delta-backed table.
- PySpark transformations are lazy until an action such as `write` or `display`.

## Mistakes / Confusions

- `COPY INTO` idempotency is file-level, not business-key dedupe.
- A clean rerun does not prove the target is semantically correct.
- Quarantined files need audit records too, otherwise reruns can keep rediscovering the same bad file.
- `VALIDATE ALL` is a pre-load safety step, not a complete data quality framework.
- `FILES` is useful for bounded manual replay, but it should not become operational bookkeeping for high-volume ingestion.
- `PATTERN` can narrow a batch but can also accidentally skip files when naming conventions drift.
- `force = true` should be incident-governed and rare.

## Revision Cards

Q: What does `COPY INTO` idempotency protect against?
A: Rerunning the same load and ingesting source files that were already loaded into the target.

Q: What does `COPY INTO` idempotency not protect against?
A: Duplicate business keys spread across different files.

Q: Why keep a file audit table?
A: It proves which files were loaded or quarantined, by which run, and whether force reload was used.

Q: Why quarantine malformed files?
A: To preserve bad-input evidence without silently dropping records or corrupting typed target tables.

Q: What should happen after a duplicate business key is detected?
A: Block or condition silver promotion until merge, reject, or source-remediation rules are explicit.

Q: When should `FILES` be used?
A: For bounded explicit file lists, usually manual backfill or controlled replay.

Q: When should `PATTERN` be used?
A: To restrict loading to a known source slice, after validating naming conventions.

Q: Why is `force = true` risky?
A: It can reload already-processed files and create duplicates or inconsistent replay results.

Q: What evidence should be required before force reload?
A: Prior audit record, changed hash or correction reason, owner approval, reconciliation query, backout plan, and duplicate-key remediation if needed.

Q: When should Auto Loader be preferred over `COPY INTO`?
A: High file volume, low latency, schema drift, rescued data needs, and checkpointed incremental discovery.
