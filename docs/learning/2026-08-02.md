## Theory Anchors

- Databricks Structured Streaming checkpoints and write-ahead logs provide processing guarantees by tracking query identity, state, and processed records. Deleting checkpoint files or changing checkpoint location makes the next run begin fresh, which can trigger unintended reprocessing.
- Auto Loader stores discovered-file state in the checkpoint and uses it to provide exactly-once ingestion guarantees. For long-lived or high-volume streams, Databricks recommends modern runtimes because checkpoint state management affects startup and recovery behavior.
- `AvailableNow` is the preferred incremental-batch trigger for consuming all currently available data in bounded batches. `Trigger.Once` is deprecated in recent Databricks Runtime versions.
- `cloud_files_state` is useful for inspecting Auto Loader discovered and committed files from a checkpoint, especially when diagnosing whether a file was committed, skipped, or still pending.
- Checkpoint and schema-location prefixes should not be subject to object-store lifecycle expiration. Losing checkpoint evidence turns a safe restart into a reprocess problem.

## What I Learned

- A failed stream run is recoverable when the checkpoint location, schema location, sink table, run history, and discovered-file state are explicit.
- Same-checkpoint restart is the default recovery move for a transient failure because it preserves committed source-file evidence.
- A new checkpoint against an existing sink is dangerous unless the sink is protected by a stable idempotency key.
- Bad-record recovery should preserve the malformed payload in quarantine and replay a corrected replacement from the uncommitted boundary.
- Checkpoint deletion, checkpoint relocation, and lifecycle-policy expiration are operational incidents, not routine fixes.

## Mistakes / Confusions

- Do not confuse a source-file replay boundary with a sink-table rollback boundary. The checkpoint answers "what did the stream process"; the Delta sink answers "what became visible downstream."
- Do not delete a checkpoint just to unblock ingestion. That can cause a fresh read of available files and duplicate writes.
- Do not rely on file names alone for idempotency. Use stable business/event identity plus payload identity.
- Do not run an investigation stream against the production checkpoint. Clone the checkpoint to an isolated prefix for read-only forensics.

## Revision Cards

1. **Q:** What is the safest first restart action after a transient Auto Loader failure?
   **A:** Restart with the same source path, schema location, checkpoint location, and sink table so committed-file evidence is preserved.

2. **Q:** Why is changing checkpoint location risky?
   **A:** The stream can treat available files as unseen and reprocess them unless the sink blocks duplicates.

3. **Q:** What should protect a Delta sink during replay?
   **A:** A stable idempotency key, commonly derived from event identity and payload identity, plus merge or anti-join logic.

4. **Q:** When should a bad record be forward-fixed?
   **A:** When the corrupt payload can be quarantined and a corrected replacement can be replayed from the uncommitted boundary.

5. **Q:** Why clone a checkpoint?
   **A:** To inspect or debug checkpoint state without mutating the production stream checkpoint.

6. **Q:** What object-store rule should not apply to active production checkpoints?
   **A:** Lifecycle expiration that deletes checkpoint or schema-location files.
