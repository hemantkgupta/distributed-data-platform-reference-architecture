## What I Learned

Unity Catalog table recovery is different from Delta version restore.

`RESTORE TABLE ... TO VERSION AS OF` recovers table contents to an older Delta version while the table still exists. `UNDROP TABLE` recovers a dropped Unity Catalog relation within the recovery window after the table name has been removed from the active namespace.

`SHOW TABLES DROPPED` is the first recovery command after an accidental drop. It gives the dropped table name, table ID, deletion timestamp, creator, owner, and table type. If more than one dropped relation has the same name, the table ID becomes the safe recovery handle.

Managed and external tables have different blast radius:

- Managed Unity Catalog table drop removes metadata and marks data for deletion. It can be undropped during the configured recovery period.
- External table drop removes catalog metadata, but underlying cloud files remain. Recovery also depends on external location or storage credential privileges.
- Shallow clones of managed tables can depend on the source data files and can stop working after the source drop recovery window expires.
- Deep clones cost more but are safer as investigation evidence because they copy data.

Principal-level point: a drop incident is both a data recovery problem and a governance problem. The closure evidence should include table ID, relation type, owner, principal, grants, row count, metric comparison, downstream blast radius, and final action.

## PySpark Notes

The notebook uses PySpark to classify lifecycle recovery scenarios.

```python
cases_df = spark.table("de_learning.lifecycle_recovery_cases_day23")
recovery_decisions_df = cases_df.withColumn("recovery_action", ...)
```

SQL equivalent:

```sql
SELECT
  recovery_case_id,
  CASE
    WHEN NOT parent_schema_exists THEN 'BLOCK_PARENT_NAMESPACE_MISSING'
    WHEN NOT within_recovery_period THEN 'REBUILD_FROM_BACKUP_OR_SOURCE'
    WHEN same_name_active THEN 'RENAME_ACTIVE_RELATION_THEN_UNDROP_WITH_ID'
    ELSE 'UNDROP_TABLE'
  END AS recovery_action
FROM lifecycle_recovery_cases_day23;
```

- `spark.table(...)` loads a SQL table as a DataFrame.
- `withColumn(...)` adds derived columns such as `recovery_action` and `blast_radius`.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `~F.col(...)` means SQL `NOT`.
- `isin(...)` is SQL `IN (...)`.

## Mistakes / Confusions

- `RESTORE TABLE` and `UNDROP TABLE` solve different problems.
- `DROP TABLE` plus immediate `CREATE TABLE` is unsafe for production pipelines; prefer `CREATE OR REPLACE TABLE` for atomic replacement.
- If a new active table already uses the original name, recover with table ID after resolving the name collision.
- External table recovery can fail or remain unsafe if the external location or storage credential is missing.
- Materialized views and streaming tables have extra recovery dependencies on their backing pipeline.
- Undrop restores metadata such as privileges and properties, but constraints may need manual recreation.
- Shallow clone is not independent evidence for every drop incident; deep clone is safer for investigation.
- Recovery is incomplete without grant/owner evidence and row/metric validation.

## Revision Cards

Q: What is the difference between `RESTORE TABLE` and `UNDROP TABLE`?
A: `RESTORE TABLE` changes an existing Delta table back to an earlier version. `UNDROP TABLE` recovers a dropped Unity Catalog relation within its recovery window.

Q: What command lists dropped Unity Catalog tables that can still be recovered?
A: `SHOW TABLES DROPPED`.

Q: Why does dropped table ID matter?
A: It disambiguates multiple dropped relations with the same name and supports `UNDROP TABLE WITH ID`.

Q: What happens when a managed Unity Catalog table is dropped?
A: Metadata is removed and underlying data is marked for deletion, but the table can be undropped within the configured recovery period.

Q: What happens when an external Unity Catalog table is dropped?
A: Catalog metadata is removed, but underlying cloud files remain; recovery depends on external location and storage credential state.

Q: Why should you avoid drop-plus-create for production replacement?
A: It creates a gap where the table name does not refer to the original table identity and can break concurrent operations.

Q: What evidence should be captured after undrop?
A: Dropped table listing, table ID, owner, principal, grants, table properties, row counts, metric comparison, and final recovery action.

Q: When is `UNDROP TABLE WITH ID` preferred?
A: When multiple dropped tables share the same name or an active relation with the name must be renamed before recovering the intended dropped object.
