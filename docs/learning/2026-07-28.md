As checked on 2026-07-28, Databricks documents two Auto Loader file detection modes: directory listing and file notification. Directory listing is the default and needs only source access, but repeated listing can become expensive as directories grow. File notification mode with file events is recommended for most workloads because discovery becomes more scalable and performant.

The trigger documentation states that `AvailableNow` is the recommended replacement for `Trigger.Once` for incremental batch processing, and the production guidance recommends scheduling Auto Loader with Lakeflow Jobs and `AvailableNow` when low latency is not required. The same production guidance warns that default continuous checks can increase cloud storage API costs and that checkpoints should not be subject to lifecycle deletion policies.

The Auto Loader options documentation defines `cloudFiles.cleanSource` modes `OFF`, `DELETE`, and `MOVE`, with `OFF` as the default. It also warns that cleanup can move or delete source files, is unsafe with multiple consumers, and needs write permissions plus retention controls.

## What I Learned

Auto Loader discovery mode is a cost and latency decision.

Directory listing is simplest, but it repeatedly lists source directories. This is acceptable for small scheduled drops and early development, but it becomes a cost and startup-time problem as the directory grows.

File notification mode with file events is the better default for most production workloads. It avoids repeated full listing and gives Auto Loader an incremental discovery path. The stream still has to run frequently enough to keep file-event discovery incremental.

Classic file notification remains relevant for very latency-sensitive sources because it reads directly from the cloud queue path. That added operational setup is only worth it when latency justifies it.

`AvailableNow` is the right trigger for scheduled incremental batch ingestion. It processes data available at query start and can split work across multiple micro-batches with file and byte limits. That lets the team bound compute size instead of running a continuous stream with no low-latency requirement.

`cloudFiles.cleanSource` should be gated like a destructive operation. `MOVE` and `DELETE` can lower storage and listing cost, but they can also break slower consumers, erase replay evidence, or violate raw retention policies. A production approval needs consumer count, raw retention, bucket versioning, move destination, and `foreachBatch` behavior.

  source_id,

## Mistakes / Confusions

- Directory listing is the default, not the best production default for every source.
- File events reduce repeated listing but still need Unity Catalog/external-location setup and regular stream execution.
- Very low latency can justify classic file notifications despite higher setup burden.
- `AvailableNow` can still produce multiple micro-batches when rate limits are configured.
- `cloudFiles.maxBytesPerTrigger` is a soft limit; a batch may exceed it for the smallest input unit.
- `cloudFiles.cleanSource = DELETE` should require bucket versioning and retention checks.
- `cleanSource` is unsafe when multiple streams consume the same source location.
- Checkpoint and `cloud_files_state` evidence should be part of incident response, not only debugging after a failure.

## Revision Cards

Q: What are Auto Loader's two main file detection modes?
A: Directory listing and file notification.

Q: Which detection mode does Auto Loader use by default?
A: Directory listing.

Q: Which mode does Databricks recommend for most scalable production workloads?
A: File notification mode using file events.

Q: When might classic file notification be preferred?
A: Very latency-sensitive workloads that need to read directly from the cloud queue.

Q: What does `AvailableNow` do?
A: Processes all data available at query start as incremental batch work.

Q: Why set `cloudFiles.maxFilesPerTrigger`?
A: To cap the number of files processed per micro-batch.

Q: Why set `cloudFiles.maxBytesPerTrigger`?
A: To soft-cap the amount of data processed per micro-batch.

Q: Why is continuous directory listing expensive?
A: The stream repeatedly lists source directories and can generate many cloud storage API calls.

Q: What does `cloudFiles.cleanSource = MOVE` do?
A: Moves processed source files to an archive destination after retention conditions are met.

Q: Why is `cleanSource` risky with multiple consumers?
A: The fastest stream can move or delete files before slower consumers ingest them.

Q: What does `cloud_files_state` inspect?
A: File discovery and commit state for a stream checkpoint.

Q: Why should checkpoint paths avoid lifecycle policies?
A: Deleting checkpoint state corrupts stream progress and can force restart/reprocessing.
