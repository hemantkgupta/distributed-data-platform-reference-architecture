## Theory Anchors

- `COPY INTO` loads from files into Delta tables and is retryable and idempotent. Files already loaded from the source location are skipped, even if they changed after load.
- `COPY INTO VALIDATE` checks parseability, schema compatibility, nullability, and constraints without writing data.
- `COPY INTO` supports explicit `FILES` and `PATTERN` controls. Use those for narrow recovery loads instead of pointing at a broad root path.
- Auto Loader supports checkpointed incremental discovery. Databricks recommends file notification mode using file events for most workloads; directory listing remains the default.
- Auto Loader options include `cloudFiles.includeExistingFiles`, `cloudFiles.useManagedFileEvents`, `cloudFiles.backfillInterval`, `cloudFiles.allowOverwrites`, and `cloudFiles.cleanSource`. These options change replay, discovery, overwrite, and cost behavior.
- `cloud_files_state` returns file-level state for Auto Loader or `read_files` streams and exposes discovery/commit evidence useful for incident recovery.
- Source retention and cleanup can reduce storage and discovery cost, but move/delete behavior must be governed because it changes recovery evidence.

## What I Learned

- `COPY INTO` is a strong fit for immutable scheduled batches, especially when recovery can be narrowed with `VALIDATE`, `FILES`, or `PATTERN`.
- Auto Loader is the stronger fit for frequent arrivals because checkpointed discovery and file events reduce repeated listing work.
- Bounded backfills need two boundaries: file modification windows and business-date filters. One without the other is too easy to overrun.
- Mutable overwrites are a separate incident class. A committed path plus a changed payload hash should be held for approval instead of replayed automatically.
- A shared bronze idempotency key lets different ingestion methods converge safely on one sink.
- Quarantine is not failure avoidance; it is evidence preservation.

## Mistakes / Confusions

- Do not use `COPY INTO` against broad roots during incident recovery when an explicit `FILES` list can bound the load.
- Do not assume `COPY INTO` reloads changed source files; already-loaded files are skipped.
- Do not use `includeExistingFiles` casually after the first Auto Loader start. It changes initial discovery behavior.
- Do not use Auto Loader overwrite handling without a producer contract and explicit approval.
- Do not call a historical archive load "bounded" unless both file-time and business-date boundaries are present.
- Do not let corrupt files or partition drift enter bronze just because the operational goal is to finish a backfill.

## Revision Cards

1. **Q:** When is `COPY INTO` the right ingestion method?
   **A:** Immutable scheduled batches where files can be validated and loaded by explicit file list or pattern.

2. **Q:** What does `COPY INTO VALIDATE` do?
   **A:** It checks parseability, schema compatibility, nullability, and constraints without writing to the target table.

3. **Q:** What is the main recovery risk with `COPY INTO` and mutable files?
   **A:** Files already loaded are skipped even if the source file later changes.

4. **Q:** Why prefer Auto Loader for frequent arrivals?
   **A:** It uses checkpointed incremental discovery, and file events can reduce listing cost for production workloads.

5. **Q:** What should protect the shared bronze sink across all ingestion methods?
   **A:** A stable idempotency key plus `MERGE` or anti-join write logic.

6. **Q:** What are the two backfill boundaries used today?
   **A:** File modification time and business date.

7. **Q:** What should happen to a committed Auto Loader path that is overwritten?
   **A:** Hold for data-owner approval before enabling overwrite handling or replaying corrected data.

8. **Q:** What does `cloud_files_state` provide?
   **A:** File-level discovery and commit evidence for Auto Loader or `read_files` streams.
