As checked on 2026-07-30, the Auto Loader schema documentation states that `cloudFiles.schemaLocation` enables schema inference and evolution, and that each ingestion workload needs its own streaming checkpoint. Auto Loader samples up to the first 50 GB or 1000 files when inferring an initial schema and stores schema information under `_schemas` in the schema location.

For JSON, CSV, and XML, Auto Loader infers columns as strings by default, including nested JSON fields. `cloudFiles.inferColumnTypes = true` enables Spark-like type inference. Schema hints can enforce expected types, including nested fields and array/map child fields, while still allowing Auto Loader to infer the rest.

The documented schema evolution modes include `addNewColumns`, `addNewColumnsWithTypeWidening`, `rescue`, `failOnNewColumns`, and `none`. `addNewColumns` is the default when no schema is provided; it updates the schema location and fails the stream with an `UnknownFieldException`, then a restart resumes with the updated schema. When a schema is provided directly, `none` is the default and `addNewColumns` is not allowed, but schema hints can still be used.

The rescued data column stores columns missing from the schema, type mismatches, and case mismatches in a JSON blob with source file path. The docs also call out `readerCaseSensitive`: when case-sensitive rescue is enabled, a field with the wrong case can land in `_rescued_data` rather than the expected column.

Lakeflow pipeline `from_json` schema inference is documented as Public Preview. In that mode, `from_json` can infer and evolve JSON blob schemas when the schema argument is `NULL` and each expression has a unique `schemaLocationKey`.

## What I Learned

Schema evolution needs three pieces of state: the input files, the streaming checkpoint, and the schema location. If any one of those is missing or reused across workloads, the incident trail is weak.

`addNewColumns` is useful for compatible additive drift, but it is not a silent success path. Auto Loader updates schema state, stops with an unknown-field style failure, and expects a restart. That makes Lakeflow Jobs retry behavior part of the ingestion design.

`rescue` is the safer mode for feeds where producer drift should not automatically change the published schema. It keeps unexpected data available for review without promoting new columns.

Type widening is not the same as arbitrary type change. Widening from a narrower numeric type to a wider numeric type can be acceptable with supported runtime behavior or schema hints. A value like `"manual-review"` arriving in a DOUBLE field is an incompatible type and should be rescued/quarantined.

Case mismatches are operationally dangerous when the field is required. `Order_Id` can be rescued while `order_id` remains null, so a record can parse but still fail publication.

Corrupt JSON is not schema evolution. It belongs in bad-record or quarantine handling, and operators should not restart repeatedly expecting schema inference to fix malformed input.

## PySpark Notes

The notebook uses PySpark in Lab Part 4 to roll up drift events and choose an evolution action for each source file.

```python
events_df = spark.table("de_learning.schema_change_events_day31")
```

SQL equivalent:

```sql
SELECT
  source_file_path,
  collect_set(change_type) AS change_types,
  max(CASE WHEN change_type IN ('NEW_NESTED_FIELD', 'NEW_TOP_LEVEL_FIELD') THEN 1 ELSE 0 END) AS has_new_column
FROM schema_change_events_day31
GROUP BY source_file_path;
```

Practical syntax notes:

- `groupBy(...).agg(...)` changes the grain from one row per event to one row per source file.
- `collect_set(...)` keeps distinct change types as review evidence.
- `F.when(...).otherwise(...)` maps boolean flags to recommended modes and actions.
- `join(..., how="left")` keeps baseline files that have no schema-change events.
- `where(...)` writes only nonpublishable rows into the quarantine table.
- The DataFrame plan is lazy until `write.saveAsTable(...)` or `display(...)` runs.

## Mistakes / Confusions

- `addNewColumns` updates schema state and fails the stream; restart is expected.
- Providing a full schema changes defaults; `none` becomes default and `addNewColumns` is not allowed with a directly provided schema.
- Schema hints are not the same as casting. They tell Auto Loader how to read expected fields during inference.
- For JSON, default Auto Loader inference keeps fields as strings unless `cloudFiles.inferColumnTypes` is enabled.
- Type widening does not mean accepting incompatible string values in numeric columns.
- Case mismatches can rescue a field while leaving a required canonical field null.
- Corrupt records should not be treated as schema evolution incidents.
- Sharing checkpoint or schema-location paths across streams breaks operational evidence.

## Revision Cards

Q: What option enables Auto Loader schema inference and evolution?
A: `cloudFiles.schemaLocation`.

Q: Where does Auto Loader store schema history?
A: Under `_schemas` in the configured schema location.

Q: What is the default schema-evolution mode when no schema is provided?
A: `addNewColumns`.

Q: What happens in `addNewColumns` when Auto Loader sees a new column?
A: It updates the schema location, fails with an unknown-field style error, and resumes after restart.

Q: What mode keeps new columns out of the schema and stores them for review?
A: `rescue`.

Q: What does `addNewColumnsWithTypeWidening` add on top of `addNewColumns`?
A: Supported automatic type widening, such as narrower numeric types to wider numeric types.

Q: What should happen to an incompatible type like a string in a DOUBLE field?
A: Rescue and quarantine it rather than widening.

Q: Why are schema hints useful?
A: They predeclare expected field types while allowing inference for the rest of the payload.

Q: What does `readerCaseSensitive` affect?
A: Whether case variants are rescued or read case-insensitively.

Q: Why can a case mismatch still be a contract failure?
A: A required canonical field can remain null even though the wrong-case field exists in rescued data.

Q: What is the Lakeflow `from_json` `schemaLocationKey` for?
A: It gives each schema-inferred `from_json` expression a unique schema-tracking key inside the pipeline.

Q: Why is corrupt JSON not schema evolution?
A: The input is malformed, so changing schema will not make the record parse correctly.
