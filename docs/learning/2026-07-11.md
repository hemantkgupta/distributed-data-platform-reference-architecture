## What I Learned

Declarative Automation Bundles move Databricks deployment from manual workspace changes to versioned project configuration.

The operational model:

```text
declared bundle config -> validate -> deploy to target -> run/smoke test -> promote -> audit/rollback
```

The lab intentionally starts with unsafe production configuration:

- Prod runs as a user, not a service principal.
- Prod does not use a deployment lock.
- Prod does not fail on active runs.
- Workspace state has manual drift from the declared job resource.

This is the important habit: do not treat deployment as successful just because a command ran. Production promotion needs evidence from multiple surfaces:

- Bundle validation.
- Custom production safety checks.
- Test and smoke-run evidence.
- Approval evidence.
- Drift comparison.
- Rollback record.

Principal-level point: CI/CD is a production control plane. It should make unsafe changes difficult, explainable, and reversible.

## PySpark Notes

The notebook uses PySpark to evaluate a release gate.

```python
release_gate_df = (
    validation_summary_df
    .join(drift_summary_df, on="target_name", how="left")
    .join(test_summary_df, on="target_name", how="left")
    .join(approval_summary_df, on="target_name", how="left")
    .where(F.col("target_name") == "prod")
    .na.fill({"drift_count": 0, "failed_tests": 0, "approval_count": 0})
    .withColumn("release_decision", ...)
)
```

SQL equivalent:

```sql
SELECT
  v.target_name,
  v.blocker_failures,
  d.drift_count,
  t.failed_tests,
  a.approval_count,
  CASE
    WHEN blocker_failures = 0
     AND drift_count = 0
     AND failed_tests = 0
     AND approval_count >= 1
    THEN 'APPROVED'
    ELSE 'BLOCKED'
  END AS release_decision
FROM validation_summary v
LEFT JOIN drift_summary d USING (target_name)
LEFT JOIN test_summary t USING (target_name)
LEFT JOIN approval_summary a USING (target_name)
WHERE v.target_name = 'prod';
```

Important syntax:

- `groupBy(...).agg(...)` is SQL `GROUP BY`.
- `F.sum(F.when(...))` counts rows matching a condition.
- `join(..., how="left")` preserves the primary evidence table.
- `.na.fill(...)` replaces null aggregates with zeros.
- `withColumn(...)` adds the final decision.
- `F.lit(...)` creates literal values in expressions.

## Mistakes / Confusions

- `bundle validate` is necessary but not the whole release gate.
- Dev can run as a user; prod should normally run as a service principal.
- A manual workspace edit creates drift even if the job still runs.
- Approval alone is not enough when blocker findings or drift exist.
- Deployment history should include rollback information, not just success/failure.
- A target override is useful, but it must be reviewed because it can weaken production controls.
- CI/CD should verify both code and resource configuration.

## Revision Cards

Q: What problem do Declarative Automation Bundles solve?
A: They let Databricks jobs, pipelines, and related resources be declared, validated, deployed, and run from versioned project configuration.

Q: What is a bundle target?
A: An environment-specific deployment target such as dev, staging, or prod with its own workspace and overrides.

Q: Why should prod use a service principal?
A: It makes production job identity stable, auditable, and independent of a human user's workspace session.

Q: What is deployment drift?
A: The workspace resource state differs from the declared bundle configuration.

Q: Why is drift dangerous?
A: Future deployments and debugging assume the declared state is true, but production may be running something different.

Q: What should a release gate combine?
A: Validation results, drift checks, test outcomes, approvals, and rollback evidence.

Q: What is the difference between validation and promotion?
A: Validation checks whether configuration is deployable; promotion decides whether it is safe to deploy to a higher environment.

Q: What makes rollback operationally useful?
A: A known previous release, commit, target, deploy identity, and exact command.
