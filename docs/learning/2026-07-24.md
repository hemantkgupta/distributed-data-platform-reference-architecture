## What I Learned

`COPY INTO` and Auto Loader solve overlapping but different ingestion problems.

`COPY INTO` is a SQL command that loads files into Delta tables. It is retryable and idempotent: files already loaded from a source location are skipped on later runs. That makes it strong for SQL-first batch loads, ad hoc historical loads, modest scheduled file drops, and simple replay where file-level idempotency is enough.

Auto Loader is the stronger default for long-running or operationally complex ingestion: high file volume, low-latency arrival, schema drift, rescued data, and checkpointed incremental discovery. Auto Loader stores schema tracking under `cloudFiles.schemaLocation`, uses Structured Streaming checkpoints, and can use file events or file notification modes to avoid repeated expensive directory listing.

The production design hinge is not only file count. It is the complete source contract:

- Are files immutable after publication?
- Is latency minutes, hourly, or daily?
- Will schema drift happen?
- Do we need rescued data instead of silent loss?
- Can the workspace use file events?
- Who owns the checkpoint and schema location?
- How will replay avoid duplicates?
- Where does quarantine evidence go?

Mutable source files are risky for both patterns. `COPY INTO` skips files that were already loaded, even if the files changed later. Auto Loader generally expects immutable files by default. If upstream rewrites files, block ingestion until the source contract changes or the pipeline adds deterministic business-key dedupe.

SQL equivalent:

```sql
SELECT
  source_id,
  CASE
    WHEN schema_drift_expected OR needs_rescue_data THEN 'AUTO_LOADER'
    ELSE 'COPY_INTO'
  END AS recommended_method
FROM ingestion_source_requests_day26;
```

Important syntax:

- `spark.table(...)` loads the SQL table as a DataFrame.
- `F.col(...)` references a column inside expressions.
- `withColumn(...)` adds booleans such as `low_latency`, `large_file_scale`, and `schema_pressure`.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `like(...)` checks method families such as `COPY_INTO%` and `AUTO_LOADER%`.
- `select(...)` keeps only the columns needed by the final decision table.

## Mistakes / Confusions

- `COPY INTO` idempotency is file-level, not business-key dedupe.
- Do not enable forced reloading casually; it disables the normal skip-already-loaded behavior.
- Auto Loader checkpoints and schema locations are durable state, not temporary scratch files.
- In Unity Catalog workloads, checkpoint and schema tracking locations should be governed storage locations and should not be nested under the target table directory.
- Directory listing can become expensive because discovery work grows with source directory size.
- File events reduce discovery cost and scale better, but require setup and permissions.
- Rescued data is an operational queue, not a place to hide broken contracts forever.
- Mutable files should be blocked or handled with explicit dedupe and replay rules.

## Revision Cards

Q: When is `COPY INTO` a good fit?
A: Stable files, SQL-first batch loading, modest file counts, ad hoc or scheduled loads, and file-level idempotency.

Q: What does `COPY INTO` idempotency skip?
A: Source files already loaded into the target table from that location.

Q: Why can modified source files be risky with `COPY INTO`?
A: Already-loaded files are skipped even if modified later, unless force reload is intentionally used.

Q: When is Auto Loader a better fit?
A: High file volume, low-latency arrival, schema drift, rescue-data needs, and checkpointed incremental processing.

Q: What does `cloudFiles.schemaLocation` store?
A: Auto Loader schema tracking state, including schema evolution information.

Q: What should you protect as durable state in Auto Loader?
A: The Structured Streaming checkpoint and the schema location.

Q: Why prefer file events for Auto Loader at scale?
A: They avoid repeated full directory listing and reduce discovery cost and latency.

Q: What is the risk of mutable source files?
A: They can cause missed corrections, duplicate ingestion, or inconsistent replay unless the contract and dedupe rules are explicit.

Q: What should happen to rescued data?
A: Route it to quarantine or review, decide whether to evolve the schema or reject the source change, and keep evidence.
