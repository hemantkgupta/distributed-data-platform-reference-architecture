## What I Learned

A Lakeflow Job should be treated as an operational DAG, not a long notebook.

The key surfaces are:

- Job configuration: tasks, dependencies, retry settings, run-if conditions, owners, and output tables.
- Job run history: when the whole job started, ended, failed, repaired, or succeeded.
- Task run history: the first failed task, skipped downstream tasks, excluded alert tasks, attempt number, and error class.
- Repair scope: which tasks need to rerun after the failed task is fixed.
- Deployment configuration: whether the workspace job still matches the declared bundle/config.
- Promotion gate: whether the repaired run and deployment state are clean enough to publish.

The most important operational rule:

```text
debug the first failed task, then reason about downstream output validity
```

If `validate_bronze` fails, `build_silver` and `publish_gold` should not be trusted. If the input ingestion already succeeded, a repair run should usually restart at validation and continue downstream, rather than rerunning ingestion unnecessarily.

Principal-level point: orchestration is not just scheduling. It is a control plane for dependency correctness, failure isolation, ownership, repair, and promotion evidence.

## PySpark Notes

The notebook uses PySpark to compute retry and repair scope.

```python
incident_runs_df = (
    task_runs_df
    .where(F.col("job_run_id") == F.lit("job-run-1302"))
    .join(tasks_df.select("task_key", "depends_on", "run_if", "max_retries", "owner", "output_table"), on="task_key", how="left")
)
```

SQL equivalent:

```sql
SELECT r.*, t.depends_on, t.run_if, t.max_retries, t.owner, t.output_table
FROM lakeflow_task_runs_day13 r
LEFT JOIN lakeflow_job_tasks_day13 t
  ON r.task_key = t.task_key
WHERE r.job_run_id = 'job-run-1302';
```

Important syntax:

- `where(...)` filters a DataFrame like SQL `WHERE`.
- `F.col("column_name")` references a column.
- `F.lit("value")` creates a literal value.
- `join(..., how="left")` keeps every incident task run and adds task configuration.
- `withColumn(...)` adds operational decision columns.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `isin(...)` is SQL `IN (...)`.
- `createOrReplaceTempView(...)` bridges PySpark output back into SQL.

## Mistakes / Confusions

- A successful upstream task does not mean the whole job is safe.
- A skipped task is different from a failed task; skipped usually means dependency failure.
- An excluded task can be expected behavior, such as an alert task excluded when no upstream task failed.
- Retry budget belongs to task configuration; do not assume every task retries.
- Repair should be scoped to failed and dependent tasks when upstream input is already good.
- Promotion should be blocked by unresolved failed/skipped critical tasks or configuration drift.
- CI/CD for jobs is not only code deployment; it also includes job configuration correctness.

## Revision Cards

Q: What is a Lakeflow Job DAG?
A: A graph of tasks with dependencies and run conditions that determines execution order and failure behavior.

Q: What is the first thing to inspect when a job fails?
A: The first failed task in run history, not the last skipped downstream task.

Q: What does `SKIPPED` usually mean?
A: The task did not run because an upstream dependency failed or was skipped.

Q: What does `EXCLUDED` usually mean?
A: The task's run-if condition was not met, such as an alert task excluded when nothing failed.

Q: Why is repair scope important?
A: It avoids unnecessary reruns and focuses compute on the failed task plus downstream dependents.

Q: Why can promotion be blocked after a successful repair?
A: Deployment drift or missing evidence can still make the production job unsafe.

Q: What is deployment drift?
A: The workspace job configuration differs from the declared/reviewed job configuration.

Q: What should a promotion gate check?
A: Successful repair evidence, no unresolved promotion blockers, and no job configuration drift.
