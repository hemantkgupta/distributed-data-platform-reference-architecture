## What I Learned

Row filters restrict rows at query time. Column masks change column values at query time. Both are Unity Catalog fine-grained access controls.

The main design options:

```text
Dynamic view
  Good for one curated consumer surface.
  Useful when you want joins, reshaping, masking, and filtering in one view.

Table-level row filters and column masks
  Good for table-specific policies.
  Applied directly to individual tables and columns.

ABAC policy
  Good for centralized, consistent policy across many tagged objects.
  Policies attach at catalog/schema/table scope and apply based on governed tags.
```

Databricks documentation emphasizes that ABAC is the better scaling pattern when the same row filtering or masking rule should apply across many tables. Table-level controls are useful but can become hard to maintain at scale.

Principal-level point: do not treat row filters and masks as decorations. They are part of the publication gate. Sensitive data should not be published if required row filters or column masks are missing.

column_policy_df = (

SQL equivalent:

```sql
SELECT
  c.object_name,
  c.column_name,
  CASE WHEN r.policy_id IS NULL THEN 'FAIL' ELSE 'PASS' END AS outcome
FROM sensitive_columns_day18 c
LEFT JOIN policy_rules_day18 r
  ON c.object_name = r.target_object_name
 AND c.column_name = r.target_column_name
 AND r.active = true
WHERE c.mask_required = true;
```

Important syntax:

- `spark.table(...)` loads a SQL table into a DataFrame.
- `where(...)` filters rows like SQL `WHERE`.
- `join(..., how="left")` keeps required controls even when the policy is missing.
- `select(...)` can construct derived columns directly.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `unionByName(...)` stacks row-filter checks and column-mask checks into one result.
- `createOrReplaceTempView(...)` makes the PySpark result queryable from SQL.

## Mistakes / Confusions

- A row filter does not grant access. It restricts rows after object-level access exists.
- A column mask does not grant access. It changes visible values after access exists.
- Dynamic views are good for curated access surfaces, but they can drift if not tested.
- Table-level filters and masks are precise, but per-table maintenance can become expensive.
- ABAC scales better when many tagged objects need the same policy.
- Missing tags or missing policy rules can expose data if publication gates do not check coverage.
- Policy UDF complexity can affect query performance.
- Some security designs should fail closed when policies cannot be safely evaluated.

## Revision Cards

Q: What does a row filter do?
A: It restricts which rows a user can see at query time.

Q: What does a column mask do?
A: It changes the visible value of a column at query time, usually to hide sensitive data.

Q: Does a row filter or column mask grant access?
A: No. Object-level privileges still grant access; filters and masks restrict the visible data.

Q: When should you use a dynamic view?
A: When you want a curated consumer surface that may filter, mask, join, or reshape base data.

Q: When should you use table-level row filters and column masks?
A: When one table needs specific row or column rules managed by the table owner or a user with `MANAGE`.

Q: When should you use ABAC?
A: When the same policy should apply consistently across many tagged tables or columns.

Q: What policy gap did the Day 18 lab intentionally create?
A: `customers_external_day18.loyalty_id` requires a mask but has no active mask policy.

Q: What should happen when a sensitive publish candidate has a missing required mask?
A: Publication should be blocked until the policy gap is fixed or a documented exception is approved.
