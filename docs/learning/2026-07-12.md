## What I Learned

The first 14 days now cover all Associate domains at least once, but coverage is not the same as readiness.

The review lab makes three things explicit:

1. Objective coverage: which exam domain the prior work maps to.
2. Scenario correctness: whether the right operational decision is chosen under pressure.
3. Evidence path: which table, history view, job run, checkpoint, or gate proves the decision.

The two intentional starter mistakes are important:

- Trusting bronze file checkpoints as if they dedupe business events.
- Approving prod deployment because approval exists, even though prod identity and deployment lock are unsafe.

Those are realistic principal-level mistakes. They happen when teams confuse one evidence surface with the whole safety proof.

Principal-level point: a data engineer is production-ready when they can connect platform behavior, data correctness, governance, orchestration, and deployment evidence into one decision.

## PySpark Notes

The notebook uses PySpark to aggregate objective readiness.

```python
objective_score_df = (
    score_df
    .groupBy("objective_id")
    .agg(
        F.count("*").alias("scenario_count"),
        F.sum(F.when(F.col("outcome") == "PASS", 1).otherwise(0)).alias("passed_count")
    )
)
```

SQL equivalent:

```sql
SELECT
  objective_id,
  COUNT(*) AS scenario_count,
  SUM(CASE WHEN outcome = 'PASS' THEN 1 ELSE 0 END) AS passed_count
FROM scenario_score_after_fix_day15
GROUP BY objective_id;
```

Important syntax:

- `spark.table(...)` reads a Delta table as a DataFrame.
- `spark.sql(...)` reads a SQL query/view as a DataFrame.
- `groupBy(...).agg(...)` is SQL `GROUP BY`.
- `F.count("*")` counts rows.
- `F.sum(F.when(...))` counts conditional matches.
- `withColumn(...)` adds computed fields such as `pass_rate` and `readiness_status`.
- `.na.fill(...)` handles objectives that have coverage rows but no scenario rows yet.

## Mistakes / Confusions

- Exam objective coverage does not prove operational readiness.
- A file checkpoint proves file processing state, not business-key uniqueness.
- A Delta version proves table history, but retention determines how far back time travel can go.
- A Lakeflow repair run should be scoped to failed and dependent tasks.
- A CI/CD approval does not compensate for unsafe prod identity or drift.
- A governed view is often the right access surface even when a base table exists.
- Backfills need publication isolation; recomputing is not enough.

## Revision Cards

Q: What are the seven Associate objective areas?
A: Platform, ingestion/loading, transformation/modeling, Lakeflow Jobs, CI/CD, troubleshooting/monitoring/optimization, and governance/security.

Q: Why is `DESCRIBE HISTORY` operationally useful?
A: It shows Delta table operations and versions so you can debug bad writes and choose forward-fix or time travel.

Q: What is the difference between file idempotency and business-key idempotency?
A: File idempotency prevents loading the same file twice; business-key idempotency prevents duplicate facts/events across files.

Q: What should happen when a source adds a nullable field?
A: Usually approve as compatible if the core contract and existing consumers are safe.

Q: What is the safest response to a failed `validate_bronze` task?
A: Fix validation/quarantine issue and repair the failed task plus downstream tasks.

Q: Why block a prod bundle target that runs as a user?
A: Production jobs should use stable, auditable service-principal identity.

Q: Why use a masked governed view for analysts?
A: It enforces row filtering and column masking without exposing the base PII table.

Q: What makes backfill publication safe?
A: Pinned input, isolated output, quality checks, and atomic publication.
