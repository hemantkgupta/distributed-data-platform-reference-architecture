## Theory Anchors

- Databricks PySpark basics map DataFrame aggregations to SQL-style `GROUP BY` logic using `groupBy` and `agg`.
- `withColumn` returns a new DataFrame with an added or replaced column; it is the workhorse for validation flags.
- `F.col` returns a column expression and should be used instead of pulling values into the Python driver.
- `where` filters a DataFrame and `select` narrows the result to operationally useful columns.
- `groupBy(...).agg(...)` changes the grain of a DataFrame, which is useful for duplicate detection and validation summaries.
- `createOrReplaceTempView` creates a Spark-session-scoped temp view, letting SQL check the DataFrame result.
- DataFrame transformations are lazy until an action such as writing a table or displaying results executes the plan.
- Cast and pattern checks can return null, so production validation flags should coalesce unknown outcomes to explicit pass/fail booleans.
- A production helper should be paired with SQL-equivalent tests so ingestion teams can debug the rule without reading every method chain.

## What I Learned

- A DataFrame validation helper is just a repeatable column expression, but production value comes from naming the rule, its SQL equivalent, and its remediation path.
- `F.col` keeps logic distributed. Pulling data to Python would break the pattern and hide scale issues.
- `withColumn` is easy to overuse; for learning, it makes each gate visible, but production helper libraries should keep chained expressions readable and tested.
- Duplicate detection changes grain: first aggregate to key counts, then join counts back to the record grain.
- Failed casts must become explicit validation failures; otherwise a row can quarantine correctly while carrying an unhelpful failure reason.
- SQL reconciliation is a useful guardrail. If PySpark and SQL disagree, the helper is not ready for reuse.
- `createOrReplaceTempView` is a practical bridge when a team is stronger in SQL but needs to learn PySpark.
- Quarantine should include owner and release condition, not only a failure reason.

## PySpark Notes

Lab Part 2 builds `ingestion_validation_decisions_day37`.

- `raw_df` represents the raw Day 37 ingestion batch before validation.
- `validated_df` represents one publish or quarantine decision per source record.
- SQL equivalent: `CASE WHEN business_key IS NOT NULL AND schema_version = expected_schema_version AND ... THEN 'PUBLISH' ELSE 'QUARANTINE' END`.
- `F.col("business_key")` creates a column expression evaluated across the cluster.
- `withColumn` adds validation flags without mutating the original DataFrame.
- `F.coalesce(flag_expression, F.lit(False))` makes null validation outcomes fail closed.
- `groupBy(...).agg(F.count("*"))` finds duplicate keys before joining counts back to the row grain.
- `createOrReplaceTempView` bridges DataFrame output back into SQL for reconciliation.
- The transformations are lazy until `spark.sql(...)` and `display(...)` trigger execution.

Lab Part 4 builds `ingestion_validation_summary_day37` and `ingestion_validation_failures_day37`.

- `decisions_day37_df` represents the persisted validation decision table.
- `summary_df` changes the grain from one record per row to one row per gate action and failure reason.
- `failures_df` filters to quarantined records and selects the fields operators need.
- SQL equivalent: `SELECT record_gate_action, primary_failure_reason, count(*) FROM decisions GROUP BY 1,2`.
- `where` filters rows; `select` chooses columns; `groupBy` plus `agg` performs grouped aggregation.

## Mistakes / Confusions

- Do not skip SQL reconciliation just because the PySpark code looks correct.
- Do not treat null keys and duplicate keys as the same failure; they have different owners and replay actions.
- Do not publish stale events through normal incremental paths unless a bounded backfill has been approved.
- Do not treat PII drift as a parser problem. It is a governance and access-control incident.
- Do not build validation helpers that hide the row grain, because incident triage needs source file, event id, business key, and failure reason.

## Revision Cards

1. **Q:** What does `F.col("field")` represent?
   **A:** A distributed column expression, not a local Python value.

2. **Q:** What does `withColumn` do?
   **A:** It returns a new DataFrame with an added or replaced column.

3. **Q:** Why aggregate before detecting duplicate keys?
   **A:** Duplicate detection needs key-level counts before joining the result back to individual records.

4. **Q:** Why create a temp view from a DataFrame?
   **A:** It lets SQL users inspect and reconcile the DataFrame result in the same Spark session.

5. **Q:** Why keep a SQL-equivalent validation table?
   **A:** It proves helper behavior is deterministic and easier to debug.

6. **Q:** What should a quarantine row include?
   **A:** Source file, source system, ingestion method, event id, business key, failure reason, and validation score.

7. **Q:** What is the operational difference between stale event and duplicate key?
   **A:** Stale events need backfill approval; duplicate keys need ordering or producer replay policy.

8. **Q:** Why is PySpark lazy evaluation important?
   **A:** Transformations build a plan; execution happens only at actions such as writes, counts, or displays.
