## What I Learned

Unity Catalog governance starts with object identity.

The hierarchy to remember:

```text
metastore -> catalog -> schema -> tables/views/volumes/functions/models
```

The most important lifecycle distinction:

```text
managed table  = Databricks owns metadata and data lifecycle
external table = Databricks owns metadata; cloud storage owner owns files
view           = logical access contract; no physical data ownership
volume         = governed file path for non-tabular files
```

Managed vs external is not just a storage detail. It changes drop behavior, cleanup responsibility, ownership boundaries, incident response, and audit review.

Principal-level point: before granting access or dropping objects, identify object type, storage type, owner, consumers, and file lifecycle. Most production incidents come from treating those as obvious when they are not.

## PySpark Notes

The notebook uses PySpark to classify lifecycle risk.

```python
lifecycle_df = (
    objects_df
    .join(assets_df.select(...), on="object_name", how="left")
    .join(broad_reader_grants_df, on="object_name", how="left")
    .na.fill({"broad_reader_grant_count": 0})
    .withColumn("drop_risk", ...)
    .withColumn("recommended_action", ...)
)
```

SQL equivalent:

```sql
SELECT
  o.object_name,
  o.object_type,
  o.storage_kind,
  COALESCE(g.broad_reader_grant_count, 0) AS broad_reader_grant_count,
  CASE
    WHEN o.storage_kind = 'managed' THEN 'DROPS_METADATA_AND_DATA'
    WHEN o.storage_kind = 'external' THEN 'DROPS_METADATA_ONLY'
    ELSE 'NO_PHYSICAL_DATA'
  END AS drop_risk
FROM uc_object_hierarchy_day16 o
LEFT JOIN external_assets_day16 a
  ON o.object_name = a.asset_name
LEFT JOIN broad_reader_grants g
  ON o.object_name = g.object_name;
```

Important syntax:

- `where(...)` filters rows like SQL `WHERE`.
- `groupBy(...).agg(F.count("*"))` is SQL `GROUP BY`.
- `join(..., how="left")` keeps every object even when optional metadata is missing.
- `.na.fill(...)` replaces nulls after a left join.
- `withColumn(...)` adds computed risk and action fields.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.

## Mistakes / Confusions

- A view is not a copy of the data; it is a logical query contract.
- Dropping an external table does not mean the cloud files are deleted.
- Dropping a managed table has stronger data lifecycle implications.
- A volume is for governed file access, not a table.
- A reader group should usually get access to a governed view, not a broad base table.
- External assets require storage-owner review before cleanup.
- Ownership and grants are different: owning an object does not mean every consumer should get direct access.

## Revision Cards

Q: What is the Unity Catalog object hierarchy?
A: Metastore -> catalog -> schema -> tables/views/volumes and other governed objects.

Q: What is a managed table?
A: A table where Databricks manages both metadata and data lifecycle.

Q: What is an external table?
A: A table where Databricks manages metadata, but data files remain in external cloud storage.

Q: What happens when you drop an external table?
A: The catalog metadata is dropped; cloud files are not automatically deleted.

Q: What is a volume for?
A: Governed file access for non-tabular files or landing paths.

Q: Why expose a view to consumers?
A: A view can enforce a stable query contract and hide/restrict base table details.

Q: Why is direct base-table SELECT risky?
A: It can bypass intended governance, filtering, masking, or semantic contracts.

Q: What should you check before dropping an object?
A: Object type, storage type, owner, downstream consumers, file lifecycle, and retention needs.
