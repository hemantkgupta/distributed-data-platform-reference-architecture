## Theory Anchors

- Lakeflow Connect covers managed and customizable ingestion from enterprise applications, databases, cloud storage, message buses, and more.
- Managed connectors are governed by Unity Catalog and are powered by Lakeflow pipelines and serverless compute where supported.
- Managed database connectors ingest relational database changes with CDC; supported examples include MySQL, PostgreSQL, SQL Server, and Oracle.
- A managed database connector has a Unity Catalog connection, an ingestion gateway, staging storage in a Unity Catalog volume, an ingestion pipeline, and destination streaming tables.
- The ingestion gateway runs continuously on classic compute to capture snapshots, change logs, and metadata before source logs are truncated; the ingestion pipeline moves staged data to destination tables.
- Query-based connectors read database rows directly with a cursor column and high-water mark. They do not require a gateway or staging volume, but they do not capture every intermediate row state between scheduled runs.
- Custom connectors are for sources not supported by managed or community connectors. They are built, tested, deployed, and run in the user's Databricks workspace.
- File arrival triggers can start Lakeflow Jobs for new files in Unity Catalog volumes or external locations; debounce and minimum interval settings reduce noisy batch starts.

## What I Learned

- Lakeflow Connect is not one method. The practical decision is which managed, query-based, standard, community, custom, or fallback path fits a source contract.
- Managed database CDC is appropriate when the source supports CDC or change tracking, the connector exists, and gateway/network/source-retention requirements are satisfied.
- Query-based connectors are a lower-operational-cost database path when a cursor column is reliable and intermediate row states or deletes are not the key requirement.
- The ingestion gateway is a real operational object: it needs source connectivity, classic compute sizing, retention safety, and staging volume monitoring.
- Destination tables for managed database connectors are streaming tables, not ad hoc notebook outputs.
- Governance approval can block a technically valid connector when the source contains restricted PII.
- File arrival triggers help reduce idle compute for file-source ingestion, but they do not remove the need for checkpoint and source contract boundaries.

## Mistakes / Confusions

- Do not choose managed database CDC until source CDC/change tracking, source privileges, network reachability, gateway sizing, and source retention are checked.
- Do not use query-based connectors when every intermediate row state or every delete event must be captured.
- Do not treat managed connectors as zero-operations. They still need monitoring, release gates, and rollback evidence.
- Do not provision credentials before governance and source ownership approve the ingestion contract.
- Do not use a custom connector before checking managed, standard, and community connector fit.

## Revision Cards

1. **Q:** When does Lakeflow Connect managed database CDC fit?
   **A:** When the database has a supported connector, source CDC/change tracking is available, source retention is safe, and gateway/staging/target requirements are acceptable.

2. **Q:** What are the main managed database connector components?
   **A:** Unity Catalog connection, ingestion gateway, staging storage volume, ingestion pipeline, and destination streaming tables.

3. **Q:** What does the ingestion gateway do?
   **A:** It continuously extracts snapshots, change logs, and metadata before source logs can be truncated.

4. **Q:** When does a query-based connector fit?
   **A:** When a reliable monotonically increasing cursor column can track changed rows and scheduled latest-state ingestion is enough.

5. **Q:** What does a query-based connector not guarantee?
   **A:** It does not capture every intermediate row state between scheduled runs.

6. **Q:** When should a source be held even if a connector exists?
   **A:** When governance, credentials, source ownership, networking, or source prep is incomplete.

7. **Q:** What is a custom connector for?
   **A:** A source without a suitable managed or community connector where you must build, test, deploy, and run connector logic yourself.

8. **Q:** What should be in a connector release gate?
   **A:** Decision pattern, incident status, credential health, gateway/staging health, source retention, quarantine status, fallback plan, and rollback evidence.
