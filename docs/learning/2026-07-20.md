## What I Learned

Delta incident recovery has three separate surfaces:

```text
history -> what operation changed the table?
time travel -> what did the table look like before the bad write?
recovery action -> restore or forward-fix?
```

`DESCRIBE HISTORY` is the incident timeline. It lets you inspect table versions, operation types, timestamps, users, parameters, and metrics. It is the first place to look when a row count, revenue number, or dashboard result suddenly changes.

Time travel is the diagnosis surface. It lets you query a table before the bad write without changing the current table. That is how you prove whether a suspected version is the known-good state.

`RESTORE TABLE` is appropriate when:

- The bad write is the latest table-changing operation.
- No valid writes happened after the bad version.
- Downstream consumers have not already acted on the bad data, or the restore action is coordinated.
- The team can preserve the bad version and recovery evidence.

Forward-fix is safer when:

- Valid writes happened after the bad write.
- Downstream consumers already received the bad data.
- You need an explicit correcting transaction rather than a rollback.
- Audit requirements prefer a visible correction over state rewind.

Principal-level point: recovery is not done when the query looks good again. It is done when the incident has a bad version, known-good version, chosen recovery action, validation result, and durable evidence row.

## PySpark Notes

The notebook uses PySpark to turn history and incident records into a recovery decision.

```python
history_df = spark.sql("DESCRIBE HISTORY de_learning.orders_recovery_day22")
incidents_df = spark.table("de_learning.recovery_incidents_day22")
```

SQL equivalent:

```sql
DESCRIBE HISTORY de_learning.orders_recovery_day22;
SELECT * FROM recovery_incidents_day22;
```

Important syntax:

- `spark.sql(...)` runs SQL and returns a DataFrame.
- `spark.table(...)` loads a SQL table as a DataFrame.
- `join(..., "left")` keeps incidents even when the history row is missing.
- `F.col(...)` references DataFrame columns.
- `~F.col("downstream_published")` means SQL `NOT downstream_published`.
- `F.when(...).otherwise(...)` is SQL `CASE WHEN`.
- `createOrReplaceTempView(...)` makes the PySpark result queryable from SQL cells.
- PySpark remains lazy until an action such as `display(...)` runs.

## Mistakes / Confusions

- `RESTORE` creates a new version; it does not erase the bad write from history.
- Time travel is for diagnosis and comparison; restore is a table-changing action.
- A restore can lose later valid writes if a bad write is not the latest change.
- Forward-fix is often better after downstream publication because it creates an explicit correcting transaction.
- `DESCRIBE HISTORY` is not long-term backup. Retention and `VACUUM` still matter.
- A bad state snapshot can be useful for audit and replay testing.
- The recovery runbook should include validation metrics, not just a command that succeeded.

## Revision Cards

Q: What does `DESCRIBE HISTORY` provide during an incident?
A: The versioned operation timeline: writes, updates, merges, restores, timestamps, users, parameters, and metrics.

Q: What does time travel provide during an incident?
A: A read-only way to query a known-good table version or timestamp.

Q: When is `RESTORE TABLE` appropriate?
A: When the bad write is latest, no good writes followed it, and rollback is operationally acceptable.

Q: When is forward-fix safer than restore?
A: When good writes happened after the bad write or downstream consumers already saw the bad data.

Q: Does restore erase bad history?
A: No. Restore adds a new version that returns the table to an earlier state.

Q: Why keep a bad-state snapshot?
A: For audit, root-cause analysis, and forward-fix testing.

Q: What evidence should recovery leave behind?
A: Bad version, known-good version, decision action, validation metrics, post-recovery checks, and timestamp.

Q: Why can `VACUUM` affect incident recovery?
A: It can remove data files needed for time travel to older versions.
